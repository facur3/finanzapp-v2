# FinanzApp mobile: internationalization

Updated 2026-09-24 (Producto 23.1B2). Applies to the Expo app in `apps/mobile`. The web
app keeps its own copy. Read with [decision 001](decisions/001-native-mobile.md) and the
roadmap's Producto 23.1 section.

## 1. What exists today

| Layer | Where | Responsibility |
| --- | --- | --- |
| Locale | `src/i18n/locale.ts` | Two registries: `LANGUAGES` (words) and `REGIONS` (separators, date order, clock, meaning of "$"). `AppLocale` = language × region. Separate release gates (`RELEASED_LANGUAGES = ['es']`, `RELEASED_REGIONS = ['AR']` until 23.1C). |
| Preferences | `preference.ts`, `store.ts`, `provider.tsx` | Two key-value keys outside the ledger and backups; a live store; `useI18n()` re-renders consumers in place, nothing remounts. |
| Formats | `format.ts`, `bind.ts` | Dates, months, relative days, counts, percentages, money presentation, currency names. Money stays integer minor units; formatting is string transforms. |
| Catalogues | `messages/<language>/<module>.ts` | One module per functional area (below). `messages/es/index.ts` is the reference; every other language is typed against it. |
| Lookup | `messages.ts` | The single typed entry: `t(key, params)`, `{placeholders}`, CLDR plurals through `Intl.PluralRules`. |
| Errors | `errors.ts` | Shows a caught message in the reader's language (see §5). |
| Categories | `ui/appearance.ts` (`localizedCategoryLabel`) | Built-in category names by identity key; the person's names never translated (see §6). |

Screens and components only call `useI18n()`. Pure modules take a `Translate`
parameter with a Spanish default. There is no translation logic inside components,
and the domain, SQLite, backups and money presentation do not know the language.

### Modules

`common` (buttons, selectors, amount, movement and account kinds, counts), `navigation`
(tabs, every header, boot), `home`, `activity`, `forms` (entry and transfer forms),
`categories` (built-in names), `preferences`, `errors`, `reports`, `cards`, `debts`,
`accounts`, `budgets`, `recurring`, `category-manager`, `backup`, `settings`, `assistant`.
A module owns its top-level namespaces; two modules never share one. A new area adds a
module to both `index.ts` files; the English module's type (`Pick<Messages, …>`) makes a
missing key a compile error in the module that owns it.

### Plurals

A plural entry has `one` and `other` (the Spanish reference) and may add `zero`, `two`,
`few`, `many` for languages that use them. `pluralCategory(language, count)` asks
`Intl.PluralRules` (available in Hermes on iOS) and falls back to one/other; a category
a catalogue lacks reads `other`. Spanish "many" (millions, compact notation) falls back
to `other`. `npm run i18n:check` requires, per language, every category its rule uses
for whole numbers 0–1000 (Arabic six, Russian and Polish four, Japanese one).

## 2. Rules for new copy

1. Every visible string, placeholder, alert, VoiceOver label and hint is
   `t('area.place.meaning')`. Keys name the place and the meaning, never the wording.
2. Write a `/** … */` comment above a key whose context is not obvious (where it
   appears, what fills the placeholders, a Spanish example). It is exported as the
   translator's context.
3. Counts are plural entries, never `n === 1 ? … : …` in code.
4. Dates and amounts go through `useI18n()` formatters, never hand-written month arrays.
5. Never base logic on a translated string; compare ids and kinds.
6. A form's own error is stored as its key and translated when shown by `ErrorMessage`.
7. User data (merchants, accounts, notes, custom and renamed categories) is never translated.
8. Keep English about as long as Spanish in segments (≤ 13 characters), tab and
   quick-action captions (≤ 11), buttons and headers (≤ 24); a test enforces these.

## 3. Tools (local, no service, no dependency)

From `apps/mobile`:

| Command | What it does |
| --- | --- |
| `npm run i18n:extract` | Scans `app/` and `src/` for copy written outside the catalogue (string literals, JSX text, literal `label`/`title`/`placeholder`/VoiceOver attributes). Exits 1 with file:line. Justified exceptions: `i18n/extract-allow.json` (file → reason) or a `// i18n-ignore` comment on the line. |
| `npm run i18n:check` | Every language against Spanish: missing or extra keys, different placeholders, plural categories the language needs, empty text (errors); translations made from an older Spanish text (stale, via `i18n/translations.lock.json`, which holds the hash of the Spanish text each translation was reviewed against); `--verbose` lists text identical to Spanish. `--strict` fails on stale. `-- --accept en` records a language as reviewed. |
| `npm run i18n:export -- <lang> [--all]` | Writes `i18n/work/<lang>.json` (ignored by git): for each missing or stale key, the Spanish source, the English reference, the context comment, its module, placeholders, the plural categories the language needs, the glossary terms it contains and the current translation. It is the brief for AI-assisted translation or the upload to a platform. |
| `scripts/i18n/pseudo.mjs` | Pseudo-locales for layout tests: "long" (+40 %, accented, bracketed) and "rtl" (Unicode right-to-left embedding), placeholders intact. |

`tests/translation.node.ts` runs extract, check (strict), export and pseudo in CI.

`i18n/glossary.json` holds the financial terms with one meaning each (gasto/expense,
movimiento/transaction, saldo registrado/recorded balance, disponible/available — never
net worth, resumen/statement, cierre/closing date, vencimiento/due date, cobro/collection,
deshacer/undo — never delete, borrador/draft…). Add a term before translating a new
concept; the export attaches it to every key that contains it.

## 4. Adding a language (process)

1. **Decide** the language and whether it needs a region (a region is only needed when
   separators, date order or clock differ from an existing one).
2. **Brief:** `npm run i18n:export -- fr --all`.
3. **Draft with AI:** give the brief file to a model with the glossary and the
   instruction in the file. The model returns the same JSON with `translation` filled
   (plural objects for plural keys). Never send user data; the brief contains only
   interface copy. Paid APIs only after the owner configures and approves the account.
4. **Assemble:** create `messages/fr/<module>.ts` files mirroring `en/` (a small
   import script can be added then; the first extra language is the moment to write it,
   typed against `Messages`), add `fr` to `LANGUAGES` and to the catalogue map in
   `messages.ts`, add month/weekday tables and word rules to `format.ts`.
5. **Validate:** `npm run typecheck`, `npm run i18n:check`, the test suite, a
   pseudo-long pass, then a native speaker reviews the financial terms against the
   glossary. `npm run i18n:check -- --accept fr` records the reviewed source.
6. **Layout:** run the app with the language on a small iPhone at the largest Dynamic
   Type; fix wording, not layout.
7. **Release:** add it to `RELEASED_LANGUAGES` and to `expo-localization`'s
   `supportedLocales` (native rebuild; 23.1C wires the plugin), update the App Store
   localizations.
8. **Maintain:** every PR that changes Spanish leaves the other languages stale;
   `i18n:check --strict` in CI makes a reviewer either update them or accept them.

### Platform (Crowdin or similar) later

- Keep TypeScript modules as the source of truth for types. Add `export-json` /
  `import-json` scripts (one JSON per module and language, keys flattened, plural
  objects kept) so a platform sees files like `i18n/platform/es/cards.json`.
- `crowdin.yml` would map `i18n/platform/es/*.json` as sources and
  `i18n/platform/%two_letters_code%/*.json` as translations; the GitHub integration
  opens a pull request with translations; CI then runs import → typecheck → `i18n:check`.
- Upload the glossary as the platform's glossary and the context comments as key
  descriptions (already in the export). Screenshots per key can come later.
- Nothing is connected now; the choice (Crowdin, Lokalise, Tolgee self-hosted) waits
  for the owner and cost approval.

## 5. Errors: today and the migration to stable codes

Today `errors.ts` recognises a thrown domain or storage message by its exact Spanish
text (including templates such as «{name}») and shows the catalogue entry in the reader's
language. Forms and screens store their own errors as catalogue keys.

**Risks of the text coupling:** a reworded Spanish message silently stops being
translated (mitigated: a test fails when a catalogued text is no longer thrown verbatim);
two different causes with the same sentence cannot be told apart; parameters must be
parsed back out of the sentence; messages built dynamically (`Estado de ${what}`) need
special cases; the domain keeps user-facing Spanish inside business rules; and any new
throw is untranslated until someone catalogues it (extract does not scan the domain).

**Migration plan (no SQLite or rule change):**
1. Add `class DomainError extends Error { code: string; params?: Record<string, string | number> }`
   in `packages/domain`, keeping `message` in Spanish so web and older callers keep working.
2. Throw `new DomainError('budget.amountPositive', 'El presupuesto debe…')` module by
   module (ledger, budgets, liabilities, recurring, recovery, storage), one PR each, with
   the code equal to the catalogue key suffix (`errors.budgets.amount`).
3. `localizeError` accepts an error object: a `code` wins, text matching stays as a
   fallback for anything not migrated; params come from `params`, not from regexes.
4. Forms keep `cause` (not only `cause.message`) in state so the code survives.
5. When every throw has a code, drop the text map and the verbatim test, and keep a test
   that every code has a catalogue entry in every language.

## 6. Categories

The persisted identity is `(kind, categoryKey(storedLabel))`; movements, budgets,
recurring rules and backups store the Spanish string. The display name comes from
`categories.<kind>.<key>` only for a built-in category the person has not renamed. A
renamed preset, a custom category and a historical string show exactly what the person
wrote in every language. Editing a built-in category in English without changing its
name does not store the English word as a rename. Search and the picker match the
displayed and the stored name, so a new language never creates duplicate categories.

## 7. Right-to-left and long languages

Not enabled. Before the first RTL language (Arabic, Hebrew, Persian, Urdu):
- `I18nManager.allowRTL(true)` and `forceRTL` per language require an app restart on
  iOS; the language screen must say so and the store must apply it before reload.
- Audit `flexDirection: 'row'` layouts, absolute positions (`left`/`right` → `start`/`end`),
  chevrons and arrows (mirror), swipe directions, the anchored amount field (numbers stay
  LTR inside an RTL line: isolate with U+2066/U+2069), charts (time axis direction is a
  product decision) and `textAlign: 'left'`.
- Test with the pseudo "rtl" catalogue and a real RTL language on device.
- Long languages (German, Finnish, Russian): run the pseudo "long" catalogue at the
  largest Dynamic Type on a 320 pt iPhone; overflow is fixed with shorter wording or a
  stacked row (`useStacked`), never by shrinking fonts below the system scale.

## 8. Libraries: evaluation

Kept: the in-house typed lookup (≈150 lines) with `Intl.PluralRules`. It gives compile-
time key checking, per-module ownership, zero runtime dependency and no bundle cost, and
covers everything the product uses (placeholders, plurals).

| Option | Gains | Costs | Verdict |
| --- | --- | --- | --- |
| FormatJS `intl-messageformat` (ICU MessageFormat) | Standard ICU syntax (`{count, plural, one {…} other {…}}`, `select` for gender/kind, nested), what Crowdin/Lokalise speak natively | ~20 kB, needs `Intl.PluralRules`/`NumberFormat` (present in Hermes), strings become syntax translators can break | **Recommended when** the first language needs `select` (grammatical gender) or a platform integration starts |
| i18next + react-i18next + ICU plugin | Ecosystem, lazy namespaces, platform plugins | Runtime context and re-render model to replace ours, weaker key typing without codegen | Not worth a migration |
| Lingui | Compile-time extraction from source, ICU | Babel macro in Metro, a different authoring style (source text as key) | Not now |

**Incremental plan if ICU is adopted:** (1) add `intl-messageformat` behind
`translate` for values that contain ICU syntax only (detect `{x, plural,`); (2) convert
plural objects to ICU strings in the platform export while keeping objects in code, or
migrate module by module; (3) keep `t(key, params)` as the only API so no screen changes.
