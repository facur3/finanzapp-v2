# FinanzApp mobile: internationalization

Updated 2026-09-25 (Producto 24R2A). Applies to the Expo app in `apps/mobile`. The web
app keeps its own copy. Read with [decision 001](decisions/001-native-mobile.md) and the
roadmap's Producto 23.1 section.

## 1. What exists today

| Layer | Where | Responsibility |
| --- | --- | --- |
| Locale | `src/i18n/locale.ts` | Two registries: `LANGUAGES` (words) and `REGIONS` (separators, grouping, date order, separator and padding, clock, meaning of "$"; since 24R2A derived from the 257-region catalogue with the hand-written `REGION_REGISTRY` of AR/US winning), plus `SPEECH_REGIONS` (each language's home region: the decimal mark it is spoken with and the date wheel's locale). `AppLocale` = language × region. Separate release gates (`RELEASED_LANGUAGES = ['es', 'en']`, `RELEASED_REGIONS = ['AR', 'US']`); the regions' release plan by convention family is `region-release.ts` (§11a.6). |
| Preferences | `preference.ts`, `store.ts`, `provider.tsx` | Two key-value keys outside the ledger and backups; a live store; `useI18n()` re-renders consumers in place, nothing remounts. The device is re-read on return to the foreground and on iOS's locale-change event (§10). |
| Formats | `format.ts`, `bind.ts` | Dates, months, relative days (also inline: "vence hoy"), day and month in the region's order, counts, percentages, money presentation (visible: region; VoiceOver: the language's decimal mark, no grouping), currency names, the date wheel's locale (the language's home locale), `speechLanguage` for VoiceOver. Money stays integer minor units; formatting is string transforms. |
| Native | `app.config.ts` | `expo-localization` `supportedLocales.ios` (= `RELEASED_LANGUAGES`), `CFBundleDevelopmentRegion` 'es', `UIPrefersShowingLanguageSettings` (§10). |
| Amount entry | `ui/money-input.ts` (`AmountInput`), `AmountField` | Typing and pasting in the region's separators and grouping (`i18n/grouping.ts`, shared with the formatters); the form's draft stays in the ledger notation (§9, §11a.6). |
| Catalogues | `messages/<language>/<module>.ts` | One module per functional area (below). `messages/es/index.ts` is the reference; every other language is typed against it. |
| Lookup | `messages.ts` | The single typed entry: `t(key, params)`, `{placeholders}`, CLDR plurals through `Intl.PluralRules` where the engine has it (not Hermes on iOS: see Plurals). |
| Errors | `errors.ts` | Shows a caught message in the reader's language (see §5). |
| Categories | `ui/appearance.ts` (`localizedCategoryLabel`) | Built-in category names by identity key; the person's names never translated (see §6). |
| Currencies | `currencies/<language>.ts` (generated from CLDR), `format.ts` | Currency and territory names per language, generated by `npm run currency:generate`: CLDR is the translation, so they are data, not catalogue copy (exempted from `i18n:extract`). A new language adds its module; a currency CLDR does not name in it shows its ISO code. See [docs/currency.md](currency.md). |

Screens and components only call `useI18n()`. Pure modules take a `Translate`
parameter with a Spanish default. There is no translation logic inside components,
and the domain, SQLite, backups and money presentation do not know the language.

### Modules

`common` (buttons, selectors, amount, movement and account kinds, counts), `navigation`
(tabs, every header, boot), `home`, `activity`, `forms` (entry and transfer forms),
`categories` (built-in names), `preferences`, `errors`, `reports`, `cards`, `debts`,
`accounts`, `budgets`, `recurring`, `category-manager`, `backup`, `settings`, `assistant`.
A module owns its top-level namespaces; two modules never share one. A new area adds a
module to both `index.ts` files; the English module's type (`Pick<Messages, …>`) makes a
missing key a compile error in the module that owns it.

### Plurals

A plural entry has `one` and `other` (the Spanish reference) and may add `zero`, `two`,
`few`, `many` for languages that use them. `pluralCategory(language, count)` asks
`Intl.PluralRules` and falls back to one/other; a category a catalogue lacks reads
`other`. **Hermes on iOS has no `Intl.PluralRules`** (its `Intl` defines only `Collator`,
`DateTimeFormat` and `NumberFormat`: `lib/VM/JSLib/Intl.cpp` at `hermes-v250829098.0.17`,
the engine React Native 0.86 ships; verified in Producto 24A), so on the iPhone the
one/other fallback always runs. That is exact for Spanish and English. Before a language
with other categories (Arabic, Russian, Polish) is released, its CLDR plural rules must
become a committed table like the currency data ([docs/currency.md](currency.md)), or
Node tests would pass while the device picks the wrong form. Spanish "many" (millions, compact notation) falls back
to `other`. `npm run i18n:check` requires, per language, every category its rule uses
for whole numbers 0–1000 (Arabic six, Russian and Polish four, Japanese one).

## 2. Rules for new copy

1. Every visible string, placeholder, alert, VoiceOver label and hint is
   `t('area.place.meaning')`. Keys name the place and the meaning, never the wording.
2. Write a `/** … */` comment above a key whose context is not obvious (where it
   appears, what fills the placeholders, a Spanish example). It is exported as the
   translator's context.
3. Counts are plural entries, never `n === 1 ? … : …` in code.
4. Dates and amounts go through `useI18n()` formatters, never hand-written month arrays.
5. Never base logic on a translated string; compare ids and kinds.
6. A form's own error is stored as its key and translated when shown by `ErrorMessage`.
7. User data (merchants, accounts, notes, custom and renamed categories) is never translated.
8. Keep English about as long as Spanish in segments (≤ 13 characters), tab and
   quick-action captions (≤ 11), buttons and headers (≤ 24); a test enforces these.

## 3. Tools (local, no service, no dependency)

From `apps/mobile`:

| Command | What it does |
| --- | --- |
| `npm run i18n:extract` | Scans `app/` and `src/` for copy written outside the catalogue (string literals, JSX text, literal `label`/`title`/`placeholder`/VoiceOver attributes). Exits 1 with file:line. Justified exceptions: `i18n/extract-allow.json` (file → reason) or a `// i18n-ignore` comment on the line. |
| `npm run i18n:check` | Every language against Spanish: missing or extra keys, different placeholders, plural categories the language needs, empty text (errors); translations made from an older Spanish text (stale, via `i18n/translations.lock.json`, which holds the hash of the Spanish text each translation was reviewed against); `--verbose` lists text identical to Spanish. `--strict` fails on stale. `-- --accept en` records a language as reviewed. |
| `npm run i18n:export -- <lang> [--all]` | Writes `i18n/work/<lang>.json` (ignored by git): for each missing or stale key, the Spanish source, the English reference, the context comment, its module, placeholders, the plural categories the language needs, the glossary terms it contains and the current translation. It is the brief for AI-assisted translation or the upload to a platform. |
| `scripts/i18n/pseudo.mjs` | Pseudo-locales for layout tests: "long" (+40 %, accented, bracketed) and "rtl" (Unicode right-to-left embedding), placeholders intact. |

`tests/translation.node.ts` runs extract, check (strict), export and pseudo in CI.

`i18n/glossary.json` holds the financial terms with one meaning each (gasto/expense,
movimiento/transaction, saldo registrado/recorded balance, disponible/available — never
net worth, resumen/statement, cierre/closing date, vencimiento/due date, cobro/collection,
deshacer/undo — never delete, borrador/draft…). Add a term before translating a new
concept; the export attaches it to every key that contains it.

## 4. Adding a language (process)

1. **Decide** the language and whether it needs a region (a region is only needed when
   separators, date order or clock differ from an existing one).
2. **Brief:** `npm run i18n:export -- fr --all`.
3. **Draft with AI:** give the brief file to a model with the glossary and the
   instruction in the file. The model returns the same JSON with `translation` filled
   (plural objects for plural keys). Never send user data; the brief contains only
   interface copy. Paid APIs only after the owner configures and approves the account.
4. **Assemble:** create `messages/fr/<module>.ts` files mirroring `en/` (a small
   import script can be added then; the first extra language is the moment to write it,
   typed against `Messages`), add `fr` to `LANGUAGES` and to the catalogue map in
   `messages.ts`, add month/weekday tables and word rules to `format.ts`.
5. **Validate:** `npm run typecheck`, `npm run i18n:check`, the test suite, a
   pseudo-long pass, then a native speaker reviews the financial terms against the
   glossary. `npm run i18n:check -- --accept fr` records the reviewed source.
6. **Layout:** run the app with the language on a small iPhone at the largest Dynamic
   Type; fix wording, not layout.
7. **Release:** add it to `RELEASED_LANGUAGES` and to `supportedLocales.ios` in
   `app.config.ts` (`tests/app-config.node.ts` fails while they differ), give the
   language a home region in `SPEECH_REGIONS` (its VoiceOver decimal mark and the date
   wheel's locale), build a new native binary through EAS (Metro cannot change
   Info.plist; iOS lists the language in Settings only after that build), and update
   the App Store localizations. A catalogue can be checked before its release on
   FinanzApp Dev with `EXPO_PUBLIC_LOCALE_PREVIEW=1` (§9).
8. **Maintain:** every PR that changes Spanish leaves the other languages stale;
   `i18n:check --strict` in CI makes a reviewer either update them or accept them.

### Platform (Crowdin or similar) later

- Keep TypeScript modules as the source of truth for types. Add `export-json` /
  `import-json` scripts (one JSON per module and language, keys flattened, plural
  objects kept) so a platform sees files like `i18n/platform/es/cards.json`.
- `crowdin.yml` would map `i18n/platform/es/*.json` as sources and
  `i18n/platform/%two_letters_code%/*.json` as translations; the GitHub integration
  opens a pull request with translations; CI then runs import → typecheck → `i18n:check`.
- Upload the glossary as the platform's glossary and the context comments as key
  descriptions (already in the export). Screenshots per key can come later.
- Nothing is connected now; the choice (Crowdin, Lokalise, Tolgee self-hosted) waits
  for the owner and cost approval.

## 5. Errors: today and the migration to stable codes

Today `errors.ts` recognises a thrown domain or storage message by its exact Spanish
text (including templates such as «{name}») and shows the catalogue entry in the reader's
language. Forms and screens store their own errors as catalogue keys.

**Risks of the text coupling:** a reworded Spanish message silently stops being
translated (mitigated: a test fails when a catalogued text is no longer thrown verbatim);
two different causes with the same sentence cannot be told apart; parameters must be
parsed back out of the sentence; messages built dynamically (`Estado de ${what}`) need
special cases; the domain keeps user-facing Spanish inside business rules; and any new
throw is untranslated until someone catalogues it (extract does not scan the domain).

**Migration plan (no SQLite or rule change):**
1. Add `class DomainError extends Error { code: string; params?: Record<string, string | number> }`
   in `packages/domain`, keeping `message` in Spanish so web and older callers keep working.
2. Throw `new DomainError('budget.amountPositive', 'El presupuesto debe…')` module by
   module (ledger, budgets, liabilities, recurring, recovery, storage), one PR each, with
   the code equal to the catalogue key suffix (`errors.budgets.amount`).
3. `localizeError` accepts an error object: a `code` wins, text matching stays as a
   fallback for anything not migrated; params come from `params`, not from regexes.
4. Forms keep `cause` (not only `cause.message`) in state so the code survives.
5. When every throw has a code, drop the text map and the verbatim test, and keep a test
   that every code has a catalogue entry in every language.

## 6. Categories

The persisted identity is `(kind, categoryKey(storedLabel))`; movements, budgets,
recurring rules and backups store the Spanish string. The display name comes from
`categories.<kind>.<key>` only for a built-in category the person has not renamed. A
renamed preset, a custom category and a historical string show exactly what the person
wrote in every language. Editing a built-in category in English without changing its
name does not store the English word as a rename. Search and the picker match the
displayed and the stored name, so a new language never creates duplicate categories.

## 7. Right-to-left and long languages

Not enabled. Before the first RTL language (Arabic, Hebrew, Persian, Urdu):
- `I18nManager.allowRTL(true)` and `forceRTL` per language require an app restart on
  iOS; the language screen must say so and the store must apply it before reload.
- Audit `flexDirection: 'row'` layouts, absolute positions (`left`/`right` → `start`/`end`),
  chevrons and arrows (mirror), swipe directions, the anchored amount field (numbers stay
  LTR inside an RTL line: isolate with U+2066/U+2069), charts (time axis direction is a
  product decision) and `textAlign: 'left'`.
- Test with the pseudo "rtl" catalogue and a real RTL language on device.
- Long languages (German, Finnish, Russian): run the pseudo "long" catalogue at the
  largest Dynamic Type on a 320 pt iPhone; overflow is fixed with shorter wording or a
  stacked row (`useStacked`), never by shrinking fonts below the system scale.

## 8. Libraries: evaluation

Kept: the in-house typed lookup (≈150 lines) with `Intl.PluralRules`. It gives compile-
time key checking, per-module ownership, zero runtime dependency and no bundle cost, and
covers everything the product uses (placeholders, plurals).

| Option | Gains | Costs | Verdict |
| --- | --- | --- | --- |
| FormatJS `intl-messageformat` (ICU MessageFormat) | Standard ICU syntax (`{count, plural, one {…} other {…}}`, `select` for gender/kind, nested), what Crowdin/Lokalise speak natively | ~20 kB, needs `Intl.PluralRules` (absent in Hermes on iOS: a polyfill or data table) and `NumberFormat`, strings become syntax translators can break | **Recommended when** the first language needs `select` (grammatical gender) or a platform integration starts |
| i18next + react-i18next + ICU plugin | Ecosystem, lazy namespaces, platform plugins | Runtime context and re-render model to replace ours, weaker key typing without codegen | Not worth a migration |
| Lingui | Compile-time extraction from source, ICU | Babel macro in Metro, a different authoring style (source text as key) | Not now |

**Incremental plan if ICU is adopted:** (1) add `intl-messageformat` behind
`translate` for values that contain ICU syntax only (detect `{x, plural,`); (2) convert
plural objects to ICU strings in the platform export while keeping objects in code, or
migrate module by module; (3) keep `t(key, params)` as the only API so no screen changes.

## 9. Regional formats and amounts (Producto 23.1C1)

**Who decides what.** The language gives the words; the region gives the separators, the
order of a numeric date and the clock; the account gives the currency. Nothing else:
the device, the language or the region never change an account's currency, and ARS and
USD are the only currencies an account can hold. Since Producto 24A every other ISO 4217
currency has its catalogue entry, decimals, CLDR symbol and names, and formats correctly
(`formatMoneyAmount`, `moneyText`), but none is stored or offered before 24B; rates are 24C
([docs/currency.md](currency.md)). Since 24B1 the ledger's *type* is any ISO code and the
domain groups by the currencies present; what a new account may hold is still gated to
ARS/USD, and the generated name modules (`src/i18n/currencies/<lang>.ts`) are required by
`npm run i18n:check` for every catalogue language and exempt from `i18n:extract` by their
`GENERATED` header. Since 24B2 the amount field and every form read and write amounts with
the account's own decimals (`money-input.ts` takes the currency everywhere): the region still
gives the separators, the currency gives the decimals and the number pad, and a draft kept
across a currency change is never rewritten (`amount.kept.*` says why it cannot be saved).
The refusal sentences gained per-exponent variants (`errors.domain.decimalsDigits`,
`wholeNumbers`, `amount.paste.precisionDigits`, `precisionNone`); the two-decimal sentences
are unchanged for ARS and USD. Since 24B3 every visible and spoken amount names its currency:
the bound locale no longer offers `formatAmount` or `spokenNumber` (`formatMoneyAmount` and
`spokenMinor` take the currency; a test bans the old names in `app/` and `src/ui/`), a chooser
names every currency with one template (`currency.option`: "Pesos · ARS", "Yenes japoneses ·
JPY"), and a currency's unit in words comes from the catalogue for ARS and USD and from CLDR for
the rest (see VoiceOver below).

| | es-AR | en-AR | es-US | en-US |
| --- | --- | --- | --- | --- |
| Amount (`formatAmount`) | 1.234,56 | 1.234,56 | 1,234.56 | 1,234.56 |
| Pesos / dollars (`moneyText`) | $ 1.234,56 · US$ 1.234,56 | same | AR$ 1,234.56 · US$ 1,234.56 | same |
| Negative | −US$ 1.234,56 | same | −US$ 1,234.56 | same |
| Percentage | 12,4 % | 12,4% | 12.4 % | 12.4% |
| Numeric date · time | 22/9/2026, 14:03 | 22/9/2026, 14:03 | 9/22/2026, 2:03 p. m. | 9/22/2026, 2:03 PM |
| Long date | 22 de septiembre de 2026 | September 22, 2026 | 22 de septiembre de 2026 | September 22, 2026 |
| VoiceOver (`spokenMoney`, 23.1C2) | 1234,56 pesos | 1234.56 pesos | 1234,56 pesos | 1234.56 pesos |
| Amount field | 1.234,56 | 1.234,56 | 1,234.56 | 1,234.56 |
| Date wheel locale (23.1C2) | es_AR | en_US | es_AR | en_US |
| Day in a report insight (`formatDayMonth`) | 5/09 | 5/09 | 9/5 | 9/5 |

**One road for money.** Screens never call `formatMinorUnits` or write a currency sign or
symbol (the scan is driven by the catalogue's own symbols): visible amounts use `moneyText` /
`formatMoneyAmount` / `codedAmount` / `formatWholeUnits` from `useI18n()`, always with the
record's currency; VoiceOver sentences use `spokenMoney` / `spokenAmount` / `spokenMinor` /
`spokenPercent`; a currency's name in a sentence comes from `currencyUnit` / `currencyName`;
forms prefill with `draftFromMinor` (a test fails otherwise). The symbol and its number are
joined by a no-break space so they never split. An amount the app cannot represent exactly
shows "—" and is read as "Importe fuera de rango" (`amount.unavailable`).

**VoiceOver speaks the language's decimal mark, never a thousands separator (23.1C2).**
A label's words are in the interface language, so its decimal mark is that language's
own (`SPEECH_REGIONS`: Spanish "1234,56 pesos", English "1234.56 dollars") whatever the
screen shows, and spoken numbers are **not grouped**. A group separator is the one mark
a voice can misread by a factor of a thousand: Apple ships Spanish voices for Argentina,
Chile, Colombia, Mexico and Spain (none for the United States), and whether a voice reads
numbers by its own variety (Mexico writes 1,234.56) or by the device's Region is not
documented, so "1.234,56" could be read as "uno punto dos tres cuatro…" by some voice
and Region pair. Plain digits are the same number for every voice, and a separator
before two digits can only be a decimal (a test sweeps the four locales for any
separator followed by three digits). The screen keeps the region's grouping; budget
sentences say "pesos"/"dólares", never "$". See §10 for the voice itself.

**The unit in words (24B3).** ARS and USD keep "pesos" and "dólares"/"dollars", the amount field
keeps "pesos argentinos"/"dólares" ("Argentine pesos"/"US dollars") and the card face "pesos"/
"dólares" ("Argentine pesos"/"US dollars"): catalogued words, looked up by code, never a two-way
condition. Every other currency is read with CLDR's plural name in the interface language ("1500
yenes japoneses", "1234.567 Kuwaiti dinars"), the singular for exactly one whole unit of a currency
without decimals, and the ISO code when the language has no name (never a name in another
language). When the ledger holds another currency whose name contains a short word (CLP beside
ARS, CAD beside USD), that word is ambiguous and ARS/USD are read with their full name
("pesos argentinos", "dólares estadounidenses", "US dollars"); the set of held currencies reaches
every consumer through `HeldCurrenciesProvider` (docs/currency.md §6). A three-decimal amount is
read as "1234,567" (Spanish) or "1234.567" (English): the separator before three digits is the
currency's own fraction, which is why three-decimal currencies open only after a VoiceOver check
on an iPhone (stage 9). Plurals do not depend on `Intl.PluralRules`: the unit words are CLDR's
`one`/`other` forms chosen by the exact spoken string, and the catalogue plurals keep the
one/other rule Hermes needs (§1).

**The amount field** (`money-input.ts`, `AmountField`):
- The draft a form holds is the ledger notation ("1.234,56", what `parseMinorUnits`
  reads) in every region; the field shows it with the region's separators. A region
  change with a form open re-renders the text only: same value, same draft, same logical
  caret. The symbol follows the region ("AR$" for pesos in the United States).
- Typing: either key of the iOS decimal pad is the decimal separator. **iOS limit:** the
  pad shows the separator of the device's Region setting, and an app cannot change it;
  so an Argentine iPhone typing in the US region shows "," on the pad and the field
  writes ".". A second decimal separator, a third decimal or a fourteenth whole digit is
  ignored. The edit is measured against the last render and the raw text the native view
  may still hold, so fast typing (999 → 1.000, 999.999 → 1.000.000, or 1,000 and 1,000,000)
  never turns a group separator into a decimal and never moves the caret.
- Pasting reads the separators the text itself uses: both present → the last is the
  decimal ("1.234,56", "1,234.56" work everywhere); one kind repeated → thousands; one
  separator before one or two digits → decimals; "$", "US$", "AR$", "U$S", "ARS", "USD"
  and spaces are ignored. **Refused, never guessed:** one separator before exactly three
  digits that is not the region's group separator ("1,000" in Argentina, "1.000" in the
  United States), more than two decimals that are not zeros, text that is not a number
  ("2 cafés a 1.500"), a second decimal separator or sign once in the field, and more
  than thirteen whole digits. The field keeps its value and caret, a note under it says
  why (and VoiceOver announces it); the next accepted edit clears it.
- No floating point: the controller keeps digits as strings; minor units come only from
  the domain's parser.

**Date wheel (iOS).** `DateField` shows the native wheel (`display="spinner"`; never
`inline` or `compact`, which draw system text that ignores the locale passed) with the
interface **language and its home region**: `es_AR` for Spanish and `en_US` for English,
in all four combinations (23.1C2; 23.1C1 passed the pair). A wheel spells the month out,
so it is a worded date and follows the language like the row it opens from
(`formatDate(…, 'dayYear')`): Spanish day · month · year, English month · day · year;
the region (numeric order, separators) never reaches it. **Why not the pair:** iOS
decides the column layout from the locale it receives and the app cannot reorder
columns, and Apple's own data disagrees with the app for the mixed pairs: Apple's ICU
ships an `en_AR` locale (parent `en_001`) that is day-first ("22 September 2026") while
the app writes "Sep 22, 2026" in English, and Apple's `es_US` writes abbreviated and
numeric dates month-first and moved its long date from day-first to month-first
("MMMM d, y") in ICU-76142.4.7 (April 2026). Upstream CLDR 48 (Node 24) differs again
(es-US day-first, no en-AR), so Node cannot predict the wheel. With `es_AR`/`en_US` the
order is the same on every iOS version and matches the row. Month capitalization and
full or abbreviated names are iOS's choice. The calendar is the device's (a Japanese or
Buddhist calendar setting shows its years; the stored date is still the Gregorian
`todayKey`), because the component does not expose it. The row is read by VoiceOver as
the long date ("Fecha: 22 de septiembre de 2026"); the wheel itself is read with
VoiceOver's own voice. A language or region change with the sheet open keeps the spun
day (tested). The picker uses `onValueChange`/`onDismiss` (the deprecated `onChange`
printed a warning in FinanzApp Dev).

**Previewing before a release.** A development bundle started with
`EXPO_PUBLIC_LOCALE_PREVIEW=1 npm run start:dev-client -- --clear` widens the gate to
every language and region the build carries (`releasedForBuild`), so FinanzApp Dev can
check a catalogue before it is released. Since 24R2A the preview carries the 257
catalogue regions (their formats, the amount field and the searchable Región chooser, whose
footnote says the preview is unverified); the languages are the released two until a third
exists. A release bundle can never use it: babel-preset-expo inlines `__DEV__`
as false, so the call compiles to `releasedForBuild(undefined, false)` and returns the
release set (`tests/locale-release.node.ts` compiles `provider.tsx` for production with
and without the flag; a local export contains no `LOCALE_PREVIEW` string; no config,
`eas.json` profile or `.env` file sets it). A choice saved during a preview is applied
once its value is released: English or United States chosen in the 23.1C1 preview now
apply on FinanzApp Dev. Metro caches compiled code without taking `EXPO_PUBLIC_` values
into account, so start or export with `--clear` after changing one.

## 10. Release, native localization and live changes (Producto 23.1C2)

**Released.** `RELEASED_LANGUAGES = ['es', 'en']`, `RELEASED_REGIONS = ['AR', 'US']`. Más →
App y datos lists **Idioma** (Según el dispositivo, Español, English; each autonym is
spoken in its own language) and **Región** (Según el dispositivo, Argentina, Estados
Unidos, each with a sample of its formats). Since 24R2A both are `ChoiceScreen` (§11a.6):
«Según el dispositivo» pinned, the released values in one card. Both stay independent, persistent (the two
key-value keys of §1) and live. The store still refuses and ignores a value outside the
gate, which now only matters for a language that is not released yet.

**Native localization (`app.config.ts`, needs a new EAS build).**

| Key | Value | Why |
| --- | --- | --- |
| `CFBundleLocalizations` (plugin `expo-localization`, `supportedLocales: { ios: ['es', 'en'] }`) | es, en | Exactly `RELEASED_LANGUAGES` (a test keeps them equal), as bare language designators: catalogues are per language and the region is its own preference. iOS then offers a per-app language (Settings → Apps → FinanzApp → Idioma) listing only these two, and runs its own text in the app (edit menu Pegar/Copiar, share sheet, UIKit buttons) in the app's language. Before this, with no localizations and Xcode's development language `en`, that text was English on a Spanish iPhone. |
| `CFBundleDevelopmentRegion` | es | iOS's fallback for its own text equals the app's fallback (`DEFAULT_LANGUAGE`): an iPhone whose languages are all unsupported (Portuguese) reads Spanish in FinanzApp's text **and** in iOS's. The generated Xcode project still says `developmentRegion = en` (cosmetic: iOS reads the Info.plist key). |
| `UIPrefersShowingLanguageSettings` | true | The per-app language row is shown even to a person with a single preferred language (WWDC24 "Build multilingual-ready apps"); older iOS ignores the key. |
| `CFBundleAllowMixedLocalizations` | not set | It would let iOS draw its text in an unsupported device language (Portuguese menus next to Spanish app text). |

The object form of `supportedLocales` touches iOS only. The plugin's Android default
(`allowDynamicLocaleChangesAndroid`) adds `locale|layoutDirection` to MainActivity's
`configChanges` (no activity recreation, consistent with "nothing remounts"); Android
per-app languages (`locales_config.xml`, `resourceConfigurations`) wait for a verified
Android build.

**Which language wins.** FinanzApp's own text: an explicit Idioma in Más, else the
device list, which on iOS already starts with the per-app language chosen in Settings
(`Locale.preferredLanguages` includes it; developer-reported, to confirm on the iPhone),
else the iPhone's preferred languages, else Spanish. Region: an explicit Región in Más,
else the iPhone's Region setting (never a second preferred language), else Argentina.
iOS's own text (edit menu, share sheet, the date wheel's accessibility, VoiceOver's own
words such as "botón") follows iOS's language for the app, not an explicit choice in Más.
For one consistent language, leave Idioma on "Según el dispositivo" and choose the
language for FinanzApp in iOS Settings. The ⓘ information alerts carry their own "OK"
(`common.ok`) so they follow the interface language.

**Changes made outside the app.**
- Changing the iPhone's language or FinanzApp's language in iOS Settings **quits the
  app** (Apple: "changing the language restarts Springboard and quits running apps";
  Apple engineers on the developer forums, threads 788012 and 734483). The next launch
  reads the new list. An unsaved form or the (ephemeral) Assistant conversation is lost
  in that case only; saved data is never touched. This is iOS behaviour and cannot be
  avoided by the app.
- Changing the **Region** (or calendar, or clock) keeps the app running. With Región on
  "Según el dispositivo" the app re-reads the device on **two idempotent signals**: the
  return to the foreground (`AppState` 'active') and iOS's own
  `NSCurrentLocaleDidChangeNotification`, which expo-localization's native module emits as
  `onLocaleSettingsChanged` once Foundation has dropped its cached `Locale.current`
  (queued while the app is suspended and delivered on resume, in no documented order with
  'active'). The subscription goes through the already-probed module object
  (`requireOptionalNativeModule('ExpoLocalization')`), so a binary without the module
  still never evaluates the package. A reading that is unchanged commits nothing; a
  reading that throws keeps the last good one (never a reset, never an exception out of
  the listener).
- An explicit Región in Más ignores a device change: only the "Según el dispositivo"
  subtitle moves; screens do not re-render.
- Every form is a modal over the tabs, so an in-app change (Más) can never meet an open
  form; a Region change from iOS can, and then only the separators of the visible amount
  change (the draft, the caret, the date and the category stay).

**Nothing remounts.** The provider never keys its children; expo-router 57 keys screens
by route and applies header and tab titles from `t()` as options only; tab roots stay
mounted. A switch keeps the navigation stack, a half-typed form, an open date sheet, the
Assistant conversation and a request in flight, and never touches the ledger (the real
provider on a real reconciler in `tests/locale-switch.node.ts`; the date sheet in
`tests/date-field.node.ts`; the Assistant screen in `tests/assistant-routes.node.ts`, whose
hook harness runs effects by their dependencies like React, so an effect that aborted the
request on a language change would fail it).

**VoiceOver.** Spoken numbers: §9. **The voice:** VoiceOver speaks with the voice of the
device's language unless an element sets `accessibilityLanguage` (UIKit documents it per
element; React Native 0.86 supports it on iOS views and text). FinanzApp sets it to the
interface language **only when the interface language differs from the device's first
language** (`speechLanguage`: English chosen in Más on a Spanish iPhone, or a Portuguese
iPhone reading Spanish), on its own wrappers (`AppText`, `PressFeedback`, `Money`, the
fields, `Choice`, `ErrorMessage`, the rows) and on every other focusable element; when
they match nothing is set, so a person keeps exactly the voice chosen in iOS Settings.
Exceptions: on Idioma, "English" and "Español" are always spoken in their own language
(as iOS Settings does); an Assistant reply is content written in Spanish by the v1
server, so it keeps a Spanish voice (the device's when the device is Spanish), while the
Assistant's own questions ("What did you pay with?") follow the usual rule.
**Labels speak their amounts.** The generic components take a spoken twin next to the
visible value (`DetailRow.spokenValue`, `SelectionRow`/`SelectorCard`/`AccountField`/
`CategoryField.spokenDetail`, `AccountField.spokenDescribe` for the sheet, `AmountShortcut.spokenCaption`,
`ActionButton.spokenLabel` for "Guardar gasto · $ 1.234,50"), built with the `spoken*`
formatters; `tests/voiceover.node.ts` parses every accessibility attribute and twin in
`app/` and `src/ui/` with the TypeScript checker and fails when a visible formatter can
reach one, or when a focusable element lacks `accessibilityLanguage`. The date row is
read as the long date; chart month bars say the full month; relative days inside a
VoiceOver sentence are lower case ("próximo hoy"). Limits that remain: native stack titles and back buttons, the tab bar,
system alerts, the date wheel, VoiceOver's own words ("botón", "seleccionado") and
announcements (React Native's `announceForAccessibility` takes no language) use the
device voice, so a mixed utterance is expected with an explicit language in Más (Apple's
engineers recommend the per-app language in Settings for full consistency); whether
VoiceOver follows a per-app language set in iOS Settings, and how each Spanish voice
reads ungrouped numbers, "ARS"/"USD" codes and short months ("15 sep"), needs the
iPhone (checklist). Text read as displayed keeps the region's separators, so in en-AR and
es-US a voice may read it the other way: the Región samples, the Reportes per-day
average, change line, insight details and budget captions, the comparison lines, the card
detail captions, the timeline maximum, alert messages, the backup export date and the
typed amount (a text field is read as typed).

**Hermes Intl.** Hermes computes its default locale once per process from
`[NSLocale currentLocale]`, which now follows the app's localization (es or en) plus the
device Region. FinanzApp's formats never use it (they are tables); only the fallback of
a binary without the native module and default-locale `localeCompare` tie-breaks do.
Spanish and English collation differ only on "ñ", which never reaches the category hue
tie-break (`categoryKey` strips the tilde; first-use stamps are ASCII dates), so no
category changes colour with the new build (`tests/categories.node.ts` runs it under the
es, es-AR and en collators). List orders that compare names can change for "ñ" only.

**Checks.** Automated: the gates, the four combinations, the preferences, live
switching, the native event, the production independence of
`EXPO_PUBLIC_LOCALE_PREVIEW`, the Info.plist values and the plugin output, spoken
labels. Device evidence (checklist 23.1C2): the iOS Settings language list, system text
after the new build, relaunch on language changes, Region while running, VoiceOver in
the four combinations, the date wheel's order.

### 11a.2 Rules (unchanged since 23.1, now tested against the catalogue)

- The device's **language** and **Region** are detected independently (`readRuntimeDeviceLocales`:
  the first preferred locale's language, the Region setting) and each maps to the nearest released
  value on its own; the raw Region is kept as `detectedRegion` so the chooser can name it. A
  language without a catalogue falls back to the app's default, a region without released
  conventions to the default region, never to each other. Nothing reads the location.
- **Regional conventions** are used when the region is released; a region the catalogue knows but
  the build does not honour writes the default region's conventions and is shown as such
  ("Japón (formatos de Argentina)"), never as if its own formats were in use; a region the
  catalogue does not know is not offered.
- A person's **manual choices win and stay saved** (`LANGUAGE_PREFERENCE_KEY`, `REGION_PREFERENCE_KEY`,
  saved before applied): travel, a new device language or a changed Region setting never modify
  them (`locale-switch.node.ts`, the 24R1 travel case: Japan → United States → United Kingdom with
  a half-typed draft, the form never re-rendering). Only **"Según el dispositivo"** follows the
  system, live (foreground and iOS's locale event), and only among released regions.
- The currency of every account is independent of both preferences (docs/currency.md §1); the
  catalogue's `currencies` and `dollarSignCurrency` are search aliases and the bare-"$" rule, never a
  default for an account. The future consolidated `reportCurrency` (24C) is a fourth thing.
- Languages are published **progressively** (§12); an incomplete language is never listed.
- Backups carry no locale: a v9 file restores the same integers whatever the device says.

### 11a.3 CLDR, Intl and Hermes: what formats what

FinanzApp writes every visible format itself from pinned CLDR tables (the month and weekday
names in `format.ts`, the region catalogue): a label reads the same on every iPhone and in Node,
no float ever stands for money, and a CLDR release change is a reviewed diff, not a silent
runtime change. `Intl` is used only where a table cannot stand in, and never assumed: `probeIntl`
reports each constructor, and every use has a fallback.

| Need | Source | Fallback when the engine lacks it |
| --- | --- | --- |
| Separators, grouping, date order, clock, week start | the region catalogue (CLDR 48.2.0) | none needed: data, not Intl |
| Ordering names in the chooser | `Intl.Collator(language, { sensitivity: 'base' })` | folding comparison (`foldText`: NFD, accents dropped, lower case) |
| Plural categories | `Intl.PluralRules` (`messages.ts`) | one/other |
| The runtime locale without the native module | `Intl.DateTimeFormat().resolvedOptions().locale` | an empty list, Spanish |
| Accent-insensitive search | `String.prototype.normalize` | lower case only |

Hermes on iOS carries `Collator`, `DateTimeFormat` and `NumberFormat` only (§1); the probe makes
the absence of the rest explicit, and `regional-formats.node.ts` runs the fallbacks.

**Deliberate deviations from CLDR** (listed in the generator, checked by `region-catalogue.node.ts`):

| Region | Field | FinanzApp | CLDR | Why |
| --- | --- | --- | --- | --- |
| AR | clock | 24 h ("14:03") | 12 h (`timeData` prefers `h`) | Producto 23.1C1: everyday Argentine writing and iOS in es_AR show 24 h |

**Known simplifications** (24R2 revisits them region by region before release): a date separator
that is a period followed by a space (Korean, Hungarian) is recorded as "." and written without
the trailing period; a group separator that is a narrow no-break space (U+202F) is kept as CLDR
gives it (since 24R2A the amount field inserts, skips and pastes it); Arabic-script default digits are
never written (Latin digits everywhere, the `latn` symbols), though since 24R2A the amount field reads
them, and full-width digits, as the same digits. A cross-check against Node's ICU 78
agrees on 224 of 257 regions; the rest differ only by those digits or by the yMd skeleton's
order against the short pattern the catalogue follows.

## 12. The language expansion programme (after 24R)

Spanish and English stay the only published languages until each new one is complete. The order
follows the target markets: Portuguese (Brazil first, then Portugal), French, German, Italian,
Japanese; others as markets justify them. A language is published only when all of these are done:
the complete catalogue (`i18n:check --strict` clean, `i18n:extract` empty), a native review of
grammar and register with the financial glossary (`i18n/glossary.json`), the financial messages and
error sentences (`errors.*` and their `localizeError` mapping), the number, date and money formats

module (`npm run currency:generate`), the VoiceOver scan and the length budgets (segments, tabs,
buttons, headers), and a device pass with that language's voice. Right-to-left scripts (Arabic,

native iOS configuration (`expo-localization`'s `supportedLocales`, `CFBundleLocalizations`, which
`tests/app-config.node.ts` keeps equal to `RELEASED_LANGUAGES`) and verified with a new build; a
catalogue can be previewed in FinanzApp Dev with `EXPO_PUBLIC_LOCALE_PREVIEW=1` before its release.

The Idioma chooser shows every language by its own name (the autonym, spoken by that language's
voice, as today), gains a search field and, once the list is long, the same compact virtualized
layout as Región (§11a); an unpublished language is never listed.

## 11. The Assistant and the interface language

**Today (23.1C2).** The Assistant's own words (title, suggestions, notes, questions,
draft card, evidence rows and links) follow the interface language and are stored as
catalogue keys, so a thread on screen follows a language or region change. A change
never aborts or re-sends a request and never changes a stored amount, merchant or
category. A failure shows only the app's own note (a caught sentence such as the
contract's "Datos de captura inválidos." or an engine's JSON error never reaches the
screen). Income category chips resolve as income. Evidence rows keep the currency the
answer was computed in and speak a difference that grew as such ("42500,00 pesos más").
The request (`AssistantRequest` v1)
carries **no language**: the contract rejects unknown keys and the server prompt is in
Spanish ("en español argentino"), so a connected Assistant would answer in Spanish with
Argentine number style; its words are content and are shown as they arrive. Builds are
disconnected and no paid AI is enabled; the development fixtures reply in Spanish on
purpose (a test pins that v1 refuses a language field before any quota or model call).

**v2 request (future, not implemented).** `locale: { language: 'es' | 'en', region: 'AR' | 'US' }`:
the resolved pair the person sees (`useI18n()` at send time, never at client creation),
not the device language list, the time zone or any other setting. Two enumerated codes,
not a BCP 47 tag: the region never changes the variety of Spanish (the catalogue is
rioplatense everywhere). Facts become language-neutral: `{ id, subject: 'expenses' |
'income' | 'category', name, amountMinor, count, startISO, endISO }`, where `name` is the
category as shown (a built-in one in the interface language, a custom or renamed one
exactly as written; null for totals) and the stored spelling stays on the device for
links. Nothing else is added: no merchants, notes or account names beyond what v1 sends.

**Server.** One stable rules block for every language first (so it can be cached), then
a short locale block: the reply language (es: rioplatense with voseo, like the
interface; en: plain English) whatever language the person typed in; amounts in the
prose in the region's separators and meaning of "$" (AR 1.234,56 with $ = ARS; US
1,234.56 with $ = USD and AR$ for pesos); numbers in the person's text read with the
region's separators, and a lone separator before three digits that is not the region's
thousands separator is ambiguous (the model asks, like the amount field's paste rule).
Merchants, category words, names and the person's words are copied verbatim, never
translated or corrected; `amountMinor` is integer minor units of the stated currency;
currencies are never converted. A v1 request keeps today's behaviour.

**Rollout.** A version bump, no optional keys: the server accepts v1 unchanged and v2
(exact key set, locale required) first; only after that server is deployed where the
build points does the app send v2. A v2 request refused by an older server fails before
any quota reservation or model call. The validator returns the wire shape of the version
received (the client posts the validated object).

**Replies and categories.** Replies are shown as they arrived, never translated, never
re-asked when the language changes; new questions use the new language. Each reply
records the language it was asked in, for VoiceOver's `accessibilityLanguage`. Before the
Assistant is connected in a build with English, a draft's category word must be matched
to an existing identity (definition key or name, a stored string already used, a
built-in name in any catalogue), otherwise "Groceries" would become a second category
beside Supermercado; an unmatched word stays the person's word.

**Privacy and cost.** The two codes travel only in Assistant requests, are never logged
with prompts or stored with quota rows, and the consent screen names them. No paid call
until the owner configures and approves the provider account.

**Multilingual input (future, decided 2026-09-24, not implemented).** When real AI is
connected, the Assistant must understand a message written in any language, including one
different from the interface language, and answer in the interface language; voice needs a
transcription provider with proven multilingual coverage before it is offered. Proper
names, custom categories and the person's data are kept verbatim (no destructive
translation); ambiguous amounts, currencies and separators are asked about before a draft
exists; the AI only proposes, and nothing is recorded without the person's confirmation.
The backend receives language and region as two separate preferences and enforces quotas,
spend ceilings, cost telemetry, security and privacy. Currencies beyond ARS/USD need the
next contract version (docs/currency.md §11); since 24B1 the client refuses to send any
other currency to v1. The full flow for "Gasté 30 dólares en Steam" (merchant, amount and
currency read by the model; category suggested from the person's own; the paying account
decided by the app with one contextual question when several fit; a foreign-currency
purchase proposed when no account holds the currency; the reference rate looked up by the
app, never the model; confirmation before any write, pending kept apart from the bank's
debit) and for "¿Por qué gasté más este mes?" (verifiable aggregations, never a causal
claim the data cannot show) is specified in docs/currency.md §11.
